# 09 — UI, HUD and design system

**Owner:** `ui` (`src/ui/`)
**Consumers:** none — nothing depends on `ui`; `ui` is a leaf
**Depends on:** `items`, `player` (hard, via `static deps`); `actors`, `skills`,
`combat`, `world`, `nav`, `render`, `save`, `audio`, `ai` (soft, via `ctx.peek`)
**Status:** specification, binding. Every number here is a commitment, not a
starting point.

The interface is a DOM+CSS overlay above the WebGL canvas plus two canvas
surfaces and a small amount of geometry in `ctx.uiScene`. There is no UI
framework, no CSS library, no external font, no external image. Every value that
moves is integrated from `dt` inside `lateUpdate` — there is not one CSS
`transition`, `animation` or `@keyframes` anywhere in the shipped stylesheet,
because the capture harness pumps frames in lockstep and a wall-clock animation
would make `tools/imagediff.mjs` non-deterministic. That single rule is the
reason this document specifies durations in milliseconds and approach rates in
reciprocal seconds rather than naming CSS easings.

## 0. What this document decides

Four architectural decisions govern everything below. They are stated first
because every later number follows from them.

**D-A — state is polled, transients are pushed.**
Once per `lateUpdate`, `ui` calls `player.hudState(this._hud)` with a
preallocated `HudState` and reads it. That is the *only* path by which a
persistent value (life, mana, rage, resonance, XP, gold, cooldowns, belt counts,
level, difficulty, zone) reaches the HUD. Events (`actor:damage`, `loot:drop`,
`player:levelup`, `quest:update`, `boss:phase`, `item:identify`) are used
**exclusively to spawn transient feedback** — a damage number, a toast, a
banner, a flare. No widget derives its steady-state value from an event, so no
widget can drift when an event is missed, dropped by a throwing handler, or
replayed by the harness.

**D-B — the pixel grid is authored, never measured.**
Every panel rectangle in §3 is a computed constant. `ui` never calls
`getBoundingClientRect`, `offsetWidth` or `getComputedStyle` inside
`lateUpdate`. The two places that genuinely need a measurement (tooltip text
width, dialogue body height) measure exactly once per user action, in the
handler, writes-then-reads. This is what lets `ui` position objects in
`ctx.uiScene` arithmetically and what keeps the frame free of forced reflow.

**D-C — text that moves is drawn to a canvas; text that is clicked is a DOM
node.** Damage numbers, floating combat text and the minimap are canvas. Panels,
tooltips, item cells, ground-item labels, buttons and the HUD chrome are DOM.
This is not an aesthetic choice: 128 DOM nodes rewriting `transform` every frame
during a 25-monster fight is 128 string allocations and 128 style invalidations
per frame, and the numbers do not need hit-testing. Ground labels *are*
clickable, so they stay DOM and are budgeted at 16.

**D-D — two clocks.**
`lateUpdate(dt, ctx)` computes `rawDt = clamp(ctx.time.raw - lastRaw, 0, 0.1)`.
Everything that belongs to the *game* (orbs, bars, damage numbers, vignette,
banners, ground labels) integrates `dt`, so it freezes exactly when the
simulation freezes. Everything that belongs to the *interface* (panel open/close,
menus, hover states, the drag ghost, the pause menu) integrates `rawDt`, so it
keeps responding while paused. Nothing anywhere reads `performance.now()`.

## 1. Aesthetic direction

Claudo II's interface is a **burnt instrument**: a slab of dark, pitted metal
with a bone-white manuscript pressed into it, and one ember still alive along
the edge. The setting is ash and forgotten knowledge, so the chrome is warm-black
rather than the blue-black of every generic dark theme — the palette is built on
`#0a0908` and `#16130f`, the colour of charcoal and scorched iron, never
`#0d1117`. Type is the other half of the argument: a **manuscript serif** carries
every name, title and banner, a plain sans carries labels and body, and a
monospace carries every number. That three-voice split is what makes a
tooltip read as a page from a burnt codex rather than as a settings dialogue,
and it costs nothing, because all three are system stacks.

Nothing is rounded except the two orbs and the resonance pips — the panels are
forged plate with hard corners and 8-pixel corner brackets. Nothing has a hard
free edge either: every HUD strip that does not butt into a panel dissolves into
the frame through a mask feather, so the overlay never reads as a rectangle
pasted on a render. Saturation is rationed: the chrome is bone, ash and one
ember accent, and the only other saturated colours on screen are the five sacred
rarity hues, the six damage-element hues and the three resource fills. If a
surface is not telling the player something urgent, it is grey.

## 2. The design system

All of it is injected from `src/ui/style.js` as a single `<style id="cl2-ui">`
element, exactly as the reference project does, with the token block on
`.cl2-ui`. No preprocessor, no external stylesheet, no `@import`, no `@font-face`.

**Text size floor: 11 px at k = 1, and k never drops below 1.0** (§3.1). There is
no text anywhere in the interface below 11 physical pixels at any supported
resolution.

**The outline, not the shadow.** Every text run that can sit over the world
carries a symmetric eight-way synthesised outline rather than an offset
drop-shadow. An offset shadow reads as a web overlay and fights whatever
direction the scene key light comes from; a ring of eight equal-radius hard
shadows reads as a drawn outline and is direction-free. This is lifted verbatim
from the reference project's `--o1` / `--o2` construction and it is not
negotiable for world-anchored text.

```css
--oc: #070605;
--o1: 1.5px 0 0 var(--oc), -1.5px 0 0 var(--oc),
      0 1.5px 0 var(--oc), 0 -1.5px 0 var(--oc),
      1.1px 1.1px 0 var(--oc), -1.1px 1.1px 0 var(--oc),
      1.1px -1.1px 0 var(--oc), -1.1px -1.1px 0 var(--oc);
--o2: /* same ring at 2.0px / 1.45px */;
--sh-o1: var(--o1), 0 0 4px rgba(7,6,5,.80);   /* world-anchored text */
--sh-o2: var(--o2), 0 0 5px rgba(7,6,5,.85);   /* display text over the world */
--sh-panel: 0 1px 1px rgba(0,0,0,.85);         /* text inside a panel */
```

All lengths above are multiplied by `var(--k)` in the real stylesheet.

### 2.5 The three signature devices

**SD-1 — The Liquid Orbs.** Life and resource are two 132 px canvas-drawn
spheres flanking the plinth. The fill is a real liquid: its surface is
`level + 1.6·sin(φ₁ + 5.2·x) + 0.9·sin(φ₂ + 9.1·x)` where `φ₁ += dt·1.7` and
`φ₂ += dt·2.9`, and a 3 px specular crescent sits at the upper-left of the glass.
Behind the fill is a lighter **ghost band** showing the value from 550 ms ago,
draining at 60 % of maximum per second — so a burst of damage is *seen*, not
merely read. This is the single strongest genre signal in the interface and it
is worth its 0.18 ms.

**SD-2 — The Ember Seam.** Every panel, tooltip, banner and list row carries a
2 px vertical bar on its leading edge, gradient-masked to transparency over its
outer 12 % at both ends so it is a seam, not a stripe. Its colour is the
element's semantic: `--ember` for neutral chrome, the **rarity colour** for an
item tooltip or an item row, `--danger` for a failed requirement or a warning,
`--verdigris` for a beneficial effect. It is the interface's one saturated line
and it is how a player identifies what they are looking at from the corner of
their eye.

**SD-3 — The Ash Dissolve.** No HUD strip ever terminates in a hard rectangle
against the world. The plinth's top edge, the target-bar plate, the quest
tracker, the buff strip and the killfeed-style toast column all carry
`mask-image: linear-gradient(...)` feathering across their outer 12 %, so the
chrome dissolves into the frame. Panels, which are opaque and modal, do not
feather — the contrast between a dissolved HUD and a hard-edged panel is itself
the signal for "this is chrome" versus "this has your attention".

### 2.6 Motion

Every entry integrates from `dt` (game clock) or `rawDt` (interface clock) per
D-D. `damp(current, target, rate, dt) = target + (current − target)·e^(−rate·dt)`
is frame-rate independent and is the default; explicit parametric curves are used
only where a shape matters.

| Effect | Clock | Model | Constants |
|---|---|---|---|
| panel open | raw | `damp` opacity 0→1 and scale 0.985→1 | rate 24 /s (≈ 130 ms to 95 %) |
| panel close | raw | `damp` to 0, then `display:none` below 0.004 | rate 30 /s |
| tooltip fade | raw | `damp` opacity | rate 26 /s; 60 ms hover delay for world targets, 0 ms for cells |
| orb fill chase | game | `damp` toward the true fraction | rate 9 /s |
| orb ghost drain | game | 550 ms hold, then linear | 0.60 of max / s |
| target-bar chase | game | `damp` | rate 14 /s |
| target-bar ghost | game | 500 ms hold, then linear | 1.20 of max / s |
| XP chase segment | game | `damp` | rate 6 /s |
| cooldown sweep | game | direct: `angle = 360·remaining/total` | no smoothing |
| damage number | game | parametric over `u = t/life` | §10.1 |
| banner in | game | `easeOutBack(t/0.30)` on scale 1.06→1.00 + opacity | 300 ms |
| banner out | game | linear opacity | 250 ms |
| level-up flare | game | parametric | 900 ms, §10.5 |
| low-life vignette | game | `damp` toward `f(life)` | rate 7 /s |
| hit flash | game | `t += dt/0.19`, `a = peak·(1 − easeOutQuad(t))` | 190 ms |
| drag ghost follow | raw | `damp` toward the pointer | rate 40 /s |
| hover highlight | raw | `damp` | rate 22 /s |
| boss intro | game | parametric on tracking and opacity | 2400 ms, §10.7 |

Easing helpers live in `src/ui/util.js` and are pure functions of an integrated
`t`; using them does not violate the no-CSS-animation rule, because `t` advances
by `dt` and nothing else.

## 3. Layout

### 3.1 The scale rule and the 720p contract

```
k = clamp(viewportHeight / 1080, 1.0, 1.60) × uiScaleSetting
uiScaleSetting ∈ { 0.85, 1.00, 1.15, 1.30 }, default 1.00
```

`--k` is written once per `resize` onto the `.cl2-ui` root as a CSS variable and
every dimension in the stylesheet is `calc(N * var(--k))`. Three consequences:

1. **The interface never shrinks below its 1080p size.** At 1280×720 the HUD is
   drawn at k = 1 and simply occupies a larger fraction of the screen. This is
   what guarantees the 11 px type floor at every supported resolution.
2. **Above 1080p it grows proportionally**, capped at k = 1.60 (reached at
   1728 px of height) so a 4K screen does not get a comically large HUD.
3. **The 720p contract:** every panel's k = 1 footprint must fit inside
   **1232 × 672** px, which is 1280×720 minus the 24 px screen margin on each
   side. This is asserted by a boot-time dev check that walks the panel geometry
   table and throws on violation. `uiScaleSetting` values that would break the
   contract are disabled in the options screen at that resolution.

`resize(w, h, ctx)` is the only place `--k`, the canvas backing stores and the
`uiScene` camera are touched. Device pixel ratio for the two canvases is
`clamp(devicePixelRatio, 1, 2)`.

### 3.3 Panel geometry

Panels occupy one of three **zones**. Only one panel per zone may be open, and a
`full` panel closes every other panel when it opens.

| Panel | i18n title key | Zone | x | y | w | h | Fits 720p |
|---|---|---|---|---|---|---|---|
| inventory | `panel.inventory` | right | 1416 | 24 | 480 | 420 | ✔ 776,24 |
| character sheet | `panel.character` | left | 24 | 24 | 440 | 628 | ✔ |
| stash | `panel.stash` | left | 24 | 24 | 480 | 600 | ✔ |
| vendor | `panel.vendor` | left | 24 | 24 | 480 | 600 | ✔ |
| quest log | `panel.quests` | left | 24 | 24 | 700 | 520 | ✔ |
| dialogue | `panel.dialogue` | full | 460 | 640 | 1000 | 260 | ✔ (bottom-anchored) |
| skill tree | `panel.skills` | full | 380 | 24 | 1160 | 648 | ✔ 60,24 |
| pause / options | `panel.options` | full | 680 | 96 | 560 | 580 | ✔ 360,60 |
| confirm dialog | `panel.confirm` | full | 760 | 430 | 400 | 220 | ✔ |

**No panel ever moves.** A `left` panel is always anchored at `--pad` from the
left edge, a `right` panel always at `--pad` from the right edge, and `full`
panels are horizontally centred. At 1280×720 the inventory sits at x = 776 and
the character sheet at x = 24, leaving a 272 px window on the world between them.
Opening a second panel never re-lays out the first — this matters because a
player mid-drag must not have the target grid slide out from under the pointer.

**Height overflow.** A panel's rendered height is `min(designH, viewportH − 36·k)`.
Only *list* content scrolls (affix lists in the vendor, quest entries, options
rows, stat sheet advanced page). The inventory grid, stash grid, equipment
paperdoll and skill tree canvas are fixed-size and never scroll — they are sized
so they always fit.

**Scrollbars** are drawn by `ui`, not by the browser: `scrollbar-width: none` and
`::-webkit-scrollbar { display:none }`, replaced by a 4 px `--ash-600` track with
an `--ash-400` thumb positioned from `scrollTop / scrollHeight`, read once per
scroll event (never per frame).

### 4.1 The orbs

Each orb is one `<canvas>` of `148 × 148` CSS px (a 8 px bleed for the outer
glow) with a backing store of `148 · k · dpr` square. Two orbs, two canvases,
zero DOM children — the numeric readout is a sibling DOM node so it gets the text
outline treatment.

**Common construction (drawn every redraw, in this order):**

1. **Well** — radial gradient `#0a0908` → `#16130f`, radius 66, clipped to the
   circle. `--well` inner shadow faked as a 4 px dark rim.
2. **Ghost band** — the fill polygon at the ghost level, in `--life-ghost` (or
   the resource's ghost tint), drawn *behind* the live fill.
3. **Live fill** — the fill polygon between the meniscus curve and the bottom of
   the circle, filled with the resource's vertical gradient.
4. **Meniscus highlight** — a 2 px line along the curve at 45 % white, only
   where `level ∈ (0.02, 0.98)`.
5. **Glass** — a 3 px specular crescent from 200° to 290° at 22 % white, and a
   1 px inner rim at 12 % white.
6. **Bezel** — a 4 px ring in `--ash-500` with an `--ash-600` top-left highlight
   and a `#000` bottom-right shade; on top of that, **tick marks** at 25 / 50 /
   75 % of height, 6 px long, 1 px, at 22 % white.

The meniscus curve is sampled at 24 x-positions across the orb width:

```
surfaceY(x) = (1 − shown) · d
            + 1.6·sin(phase1 + 5.2·x/d)
            + 0.9·sin(phase2 + 9.1·x/d)          // px, d = 132
phase1 += dt · 1.70          phase2 += dt · 2.90       // wrapped to 2π
```

Wave amplitude scales to zero over the last 4 % at either end so a full or empty
orb is flat. `shown = damp(shown, true, 9, dt)`. The ghost holds for **550 ms**
after `true` drops, then falls at 0.60 of maximum per second until it reaches
`shown`.

Numeric readout: `--t-num` centred on the orb's horizontal centre at
`orbCentreY + 34`, format `412 / 540`, `--ink-1` with `--sh-o1`. Below 25 % of
maximum the numeral turns `--danger-ink`; below 12 % it also pulses scale
`1 + 0.05·beat` on the same heartbeat that drives the vignette (§10.4).

**Hover:** hovering an orb shows a small tooltip (`--t-body`) with regeneration
per second and, for mana, the current `manaCostReduction`. It uses the same
tooltip machinery as items, at e3.

#### 4.1.1 Life orb (left)

Fill `--life`. Segment ticks at every 25 %. When `lifeFraction < 0.35` the outer
bezel gains a 2 px `--danger` ring whose alpha is `0.35 + 0.35·beat`.

#### 4.1.2 Mana orb (Emberwright, Runeblade)

Fill `--mana`. Identical geometry. When a queued cast is unaffordable the whole
orb flashes a 1 px `--danger` rim for 190 ms (`ui.error` audio cue).

#### 4.1.3 Rage orb (Ravager)

Rage is **not a liquid**. The fill is a **10-step stair**: rage 0–100 maps to ten
horizontal bands of 13.2 px, each band drawn as a slightly irregular ember slab
(the irregularity is a fixed per-band offset table baked at init from the `ui`
RNG fork, never re-rolled). A partially filled band is drawn at its fractional
width from the left. This gives rage a hard, ratcheting read that cannot be
mistaken for the life orb even in peripheral vision.

- Decay indicator: while rage is decaying (`−8 /s` out of combat) a 1 px
  `--ember-dim` arrow points down at the top of the current band, and the band's
  right edge erodes rather than sliding — the erosion width is
  `bandWidth · fract(rage/10)`.
- At rage = 100 the bezel ignites: a 3 px `--ember` ring at
  `alpha = 0.55 + 0.25·sin(φ)`, `φ += dt·3.4`.

#### 4.1.4 Resonance pips (Runeblade)

### 4.7 Minimap

Two modes; both are `pointer-events: none`.

**Corner mode** (default on): a 240 × 240 canvas at (24, 24), `--edge` border,

`SettingsSave.minimapOpacity` (default 0.75). Hidden while a `left`-zone panel is

than the 96 m Ashen Wastes at a glance.

**Overlay mode** (`Tab`): a 1440 × 860 canvas centred, alpha 0.45, scale 8.0 px
per metre, drawn over the world. The game keeps running; the overlay never takes
pointer events. `Tab` toggles, `Esc` closes.

**Rendering, and why it is cheap:**

1. On `nav:rebuilt`, `ui` rasterises `nav.grid.flags` **once** into an offscreen
   canvas at 2 px per 0.5 m cell (a 192 × 192 grid becomes 384 × 384 px):
   walkable `#2a241c`, blocked transparent, `doorway` `#3a3128`, `hazard`
   `#4a2418`, `water` `#1a2630`. A 1 px `#4c4136` outline is produced by a single
   pass comparing each cell to its right/down neighbour.
2. **Explored fog** is a second 192 × 192 8-bit canvas. At 4 Hz, `ui` stamps a
   filled disc of radius 22 m around the player at `globalAlpha = 1`,
   `globalCompositeOperation = 'lighter'`. Unexplored area is composited as an
   87 %-opaque `--void` layer.
3. Per frame the minimap does: one `drawImage` of the baked layer (translated and
   scaled, **never rotated** — the map is north-up, which is the D2 convention
   and avoids re-sampling text), one `drawImage` of the fog, then ≤ 48 marker
   blits. Total ≈ 0.14 ms.

Markers, drawn in this order (last on top):

| Marker | Glyph | Colour |
|---|---|---|
| explored ground | — | baked layer |
| ground item | 3 px square | its rarity colour |
| chest | 5 px square, hollow | `--gilt` |
| portal | 7 px ring | `--property` |
| NPC | 5 px diamond | `--verdigris` |
| monster | 4 px dot | `--danger` |
| champion / unique | 6 px dot with a 1 px ring | `--property` / `#c8973f` |

### 5.3 Rolled properties — the line builder

`ui` asks `items.rolledMods(item, this._modBuf)` (§16) for a flat array of
`{ stat, value, min, max, source, affixId, kind }`. It then runs, in order:

1. **Pair merge.** Stats that are meaningless alone are merged into one line
   *when both come from the same `affixId`*:
   `minDamage`+`maxDamage` → `Adds {a} – {b} Damage`;
   `fireMin`+`fireMax` → `Adds {a} – {b} Fire Damage`; likewise cold, lightning,
   poison, magic. A poison pair additionally appends
   ` over {poisonDuration} s`.
2. **Resistance merge.** If a single `affixId` contributed **the same value** to
   three or more of the six resistances, those lines collapse into
   `All Resistances +{v} %` (or `Elemental Resistances +{v} %` when exactly the
   four elemental resists are covered). Merging is per-affix and never per-total:
   two separate `+10 Fire Resist` affixes stay two lines, because they are two
   different things a player made a decision about.
3. **Skill bonus expansion.** `skillBonuses.all` → `+{v} to All Skills`;
   `skillBonuses.tree[t]` → `+{v} to {treeName} Skills`;
   `skillBonuses.skill[s]` → `+{v} to {skillName}`.
4. **Sort** by the ordinal table below; ties break on the stat identifier's
   position in the `StatBlock` declaration order, which is fixed, so a tooltip
   is byte-identical across runs.
5. **Sign and colour.** A value whose sign is *bad for the player* renders
   `--danger-ink` regardless of source; everything else renders `--property`.
   The "bad" test is per-stat and declared in the table (`goodDirection`).

### 5.4 Requirement-not-met treatment

Evaluated with `items.canEquip(actor, item, slot)` and, for an item already
equipped, `item._cache.unusable` (§4.4 of the data model).

- The offending requirement line renders `--danger-ink` and gains a trailing `✕`.
- The tooltip's Ember Seam turns `--danger` for its whole length.
- In a container, the item's cell gains a `--danger` X at 40 % alpha drawn with
  two 2 px CSS gradients (no node), and its icon renders at
  `filter: saturate(.35) brightness(.62)`.
- On the character sheet, an equipped-but-unusable item's slot border turns
  `--danger` and the derived stat panel shows a `--danger-ink` notice
  `tooltip.unusableEquipped`.
- Requirements are evaluated against the block *without* that item, per
  `01-data-model.md` §4.4. `ui` never recomputes this; it asks `items`.

### 5.5 Unidentified state

For `rare` and `unique` items with `identified === false`:

- **Name** is the *base* name, in the rarity colour. No generated name, no
  unique name.
- Blocks 2, 8, 9 and 11 are suppressed entirely.
- Block 3 prints `Unidentified` in `#d99b2b`, and block 13 prints
  `tooltip.unidentifiedHint` — `Use a Scroll of Identify` — in italic
  `--ink-3`.
- Base statistics (block 5) and requirements (block 6) **are** shown, because the
  player can see the item's weight and reach in the world.
- The item's cell and its ground label carry a 12 px `?` glyph in the rarity
  colour at the top-right, drawn as a CSS mask, not a font glyph.

### 5.6 Comparison mode

Active while `Ctrl` is held (`ui.setCompareHeld(true)`), or permanently when
`SettingsSave.alwaysCompare` is on.

1. `ui` asks `items.slotsFor(hoveredItem)` (§16) for the candidate slots.
2. For each occupied candidate slot, up to **two**, it builds a comparison
   tooltip: identical layout, `opacity 0.86`, a `tooltip.equipped` micro label
   above the name, and a `--ink-4` seam instead of the rarity seam.
3. Placement: comparison tooltips stack on the **opposite side** of the anchor
   from the primary tooltip, top-aligned with it, 10 px apart. If there is no
   room on that side, they stack below the primary with an 8 px gap.
4. Rings produce two comparison tooltips (`ring1` and `ring2`), each labelled.
5. A two-handed weapon hovered while a shield is equipped shows the shield as a
   second comparison and prints `tooltip.twoHandWarning` under the primary.

**Delta chips.** With comparison active, every *numeric* line in the primary
tooltip that also exists in the comparison gains a right-aligned chip:

| Condition | Chip | Colour |
|---|---|---|
| primary better | `▲ +14` | `--good-ink` |
| primary worse | `▼ −6` | `--danger-ink` |
| equal | none | — |
| present only on the primary | `▲ new` | `--good-ink` |
| present only on the comparison | `▼ lost` | `--danger-ink` |

The delta is computed on the *contributed total for that stat*, obtained from
`items.statsOf(item, out)` for both items into two preallocated partials — never
by parsing the rendered text. Weapon damage compares the mean of
`(min + max) / 2` after `enhancedDamage`; defence compares `rolls.defense` after
`defensePercent`. Both comparisons name their basis in a `--ink-4` footnote so
nobody has to guess: `tooltip.compareBasis`.

### 5.7 Placement algorithm

```
place(anchorX, anchorY, w, h, vw, vh):
  GAP  = 14 * k
  EDGE = 12 * k

  // horizontal: prefer right of the anchor, then left, then clamped-centred
  x = anchorX + GAP
  if x + w > vw - EDGE:
      x = anchorX - GAP - w
      if x < EDGE:
          x = clamp(anchorX - w / 2, EDGE, vw - w - EDGE)

  // vertical: top-align to the anchor, then push up, then clamp
  y = anchorY - 8 * k
  if y + h > vh - EDGE: y = vh - EDGE - h
  if y < EDGE:          y = EDGE

  return { x, y }
```

- **Anchor.** For a container cell, the anchor is the cell's **top-right corner**
  (computed, never measured — the grid geometry is known). For a ground item or a
  world target, the anchor is the last pointer position. For a hotbar/belt/buff
  icon, the anchor is that element's top-centre and the tooltip is placed
  **above** it, flipping below only when it would leave the viewport.
- **Recompute trigger.** Placement is recomputed only when the anchor moves more
  than 2 px, the content changes, or the viewport resizes. Not per frame.
- **Height degradation ladder.** If `h > vh − 2·EDGE`, apply in this exact order
  until it fits: (a) reduce the property line-height from 18 to 16 px; (b) drop
  the lore block; (c) drop the hint row; (d) drop the item-level row; (e) accept
  the overflow and clamp `y = EDGE`. A tooltip **never** scrolls.
- The primary tooltip never overlaps the cursor: after placement, if the cursor
  point lies inside the tooltip rect, the tooltip is pushed 20 px further along
  whichever axis has the smaller escape distance.

### 5.8 Other tooltips

The same machinery renders four more kinds, all at e3 with a `--ember` seam:

| Kind | Trigger | Content |
|---|---|---|
| skill | hotbar slot, skill-tree node, buff icon | name, tree, type tag, current level, the `skills.describe()` lines, cost, cooldown, `Requires` |
| stat | character-sheet stat row | the stat's name, its value, and a source breakdown from `actor.sources` (`base / allocated / equipment / skills / status / difficulty`) |
| status | buff-strip icon | status name, magnitude with unit, stacks, remaining, source actor and skill |
| plain | anything with a `data-tip` key | one i18n string, max 3 lines |

## 6. Inventory grid and item movement

### 6.1 Geometry

| Constant | Value @ k=1 |
|---|---|
| cell | **44 × 44 px** |
| seam between cells | 1 px, drawn as part of the background, **not** a gap |
| icon inset inside a cell | 2 px each side → a 1 × 1 icon draws at 40 × 40 |
| inventory grid | 10 × 4 = 440 × 176 px |
| stash grid | 10 × 8 = 440 × 352 px |
| vendor stock grid | 10 × 8 = 440 × 352 px |
| item rect for `w × h` | `44·w − 0 × 44·h − 0`, positioned at `(44·x, 44·y)` |

**The grid background is one DOM node.** Two `repeating-linear-gradient`
backgrounds draw the 44 px lattice and the well shading; there are no 40 or 80
cell nodes. Item nodes are absolutely positioned inside it. This is the single
largest DOM saving in the interface (§13.1).

```
.cl2-grid {
  background-image:
    repeating-linear-gradient(to right,  var(--hair) 0 1px, transparent 1px 44px),
    repeating-linear-gradient(to bottom, var(--hair) 0 1px, transparent 1px 44px),
    linear-gradient(rgba(10,9,8,.55), rgba(10,9,8,.55));
  box-shadow: var(--well);
}
```

An item node contains at most three children: a `<canvas>` that blits the cached
`OffscreenCanvas` returned by `items.icon(item)` once on placement and never
again, an optional stack count, and an optional socket row. The rarity frame and
the rarity mark are drawn on the item node itself as a `box-shadow` ring and a
background mask, so they cost no node. **Three nodes per item, maximum.**

### 6.2 Placement algorithm

`ui` never implements placement itself — `items.canPlace`, `items.place`,
`items.autoPlace` and the requested `items.findPlacement` own it. The algorithm
`items` must implement, restated here because the interface's behaviour depends
on it being exactly this:

```
canPlace(container, item, x, y, ignoreUid = item.uid):
  w = base.invW ; h = base.invH
  if x < 0 or y < 0 or x + w > W or y + h > H: return false
  for cy in y .. y+h-1:
    for cx in x .. x+w-1:
      u = cells[cy*W + cx]
      if u != 0 and u != ignoreUid: return false
  return true

findPlacement(container, item):                 // first fit, row-major
  for y in 0 .. H-h:
    for x in 0 .. W-w:
      if canPlace(container, item, x, y): return { x, y }
  return null
```

**Auto-placement on pickup** uses `findPlacement` (first fit, row-major,
top-left origin). Deterministic, and it matches what a player predicts. If it
returns `null` the pickup fails with `ui.error`, a `--danger-ink` toast
`toast.inventoryFull`, and the item stays on the ground.

**Stacking.** For a stackable consumable, pickup first scans the container
row-major for an existing stack of the same `baseId` with
`quantity < consumable.stackMax` and tops it up before allocating a new cell.

### 6.3 Drag, drop, and the cursor

Pointer events only — no HTML5 drag-and-drop, no `dragstart`, no `dataTransfer`.

**Pick up** — `pointerdown` with button 0 on an item node, with no modifier:

1. `element.setPointerCapture(e.pointerId)` on the grid, so a fast drag that
   leaves the panel still delivers `pointermove`.
2. `items.takeToCursor(item)` (§16). The item leaves its container and becomes
   `items.cursorItem`; it is serialisable, so an autosave mid-drag cannot lose it.
3. `ui` records `grabOffsetX/Y` — the pointer's offset inside the item rect in
   cells, floored — so the item does not snap its top-left to the cursor. A 2 × 3
   axe grabbed by its middle stays grabbed by its middle.
4. The **drag ghost** is created at layer 60.
5. Audio `ui.inv.pickup`.

**Drag ghost:** the item's icon at 100 % size and **72 % opacity**, plus a 2 px
rarity ring, following the pointer with `damp` rate 40 on the raw clock (a
deliberate ~25 ms lag that makes the weight readable). It is `pointer-events:
none` and it is the only thing at layer 60.

**Placement preview** (updated on `pointermove`, at most once per frame):

```
cell = floor((pointerX − gridOriginX) / 44) − grabOffsetX
row  = floor((pointerY − gridOriginY) / 44) − grabOffsetY
```

A single highlight node, sized `44·w × 44·h`, is positioned at that cell:

| Result | Highlight |
|---|---|
| valid, empty | `rgba(63,143,122,.22)` fill, 1 px `--verdigris` border |
| valid, exactly one item under it | `rgba(224,98,42,.20)` fill, 1 px `--ember` border, and the item beneath gains a 1 px `--ember` outline — this is a **swap** |
| invalid (out of bounds, or ≥ 2 items under it) | `rgba(200,50,42,.20)` fill, 1 px `--danger` border |
| over an equipment slot, equippable | `--verdigris` 2 px slot border |
| over an equipment slot, requirement unmet | `--danger` 2 px slot border, and the tooltip's requirement line is forced visible |

**Drop** — `pointerup`:

| Target | Behaviour |
|---|---|
| a valid empty rectangle | `items.dropCursor(container, x, y)`; `ui.inv.place` |
| exactly one overlapping item | **swap**: `items.dropCursor` returns `{ ok:true, swapped }`; the swapped item goes onto the cursor and the drag continues, so a player can chain swaps. Ends only on a drop into empty space or `Esc` |
| an equipment slot | `items.equip(actor, item, slot)`; on failure the reason is toasted and the item stays on the cursor |
| a belt slot | allowed only for `category === 'consumable'`; otherwise `ui.inv.invalid` |
| a vendor panel | sell (with confirmation for `rare`/`unique`) |
| outside every panel, over the world | **drop to the ground**: `items.dropToGround(item, playerX, playerZ)` after a confirmation for `rare`/`unique`; forbidden while `world.isTown` is false and the ground budget is exhausted |
| an invalid rectangle | nothing happens; the item stays on the cursor; `ui.inv.invalid` |

**Cancel** — `Esc`, or the pointer leaving the window with the button still down,
calls `items.returnCursor()`, which restores the item to its original container
and cell. If that cell has since been filled (it cannot, during a modal drag, but
the API must be total) the item auto-places, and failing that drops to the ground
at the player's feet.

**Two-handed weapons.** Equipping a two-hander requires a free rectangle for the
displaced `offHand` item. `items.canEquip` reports this; `ui` shows the reason
`equip.needsRoomForOffhand` on the highlight and refuses the drop rather than
performing a partial operation.

### 6.4 Modifier moves

| Input | Behaviour |
|---|---|
| `LMB` on an item | pick up to the cursor |
| `RMB` on an item in the inventory | equip it into its first free legal slot, or use it if consumable |
| `RMB` on an equipped item | unequip to the inventory (fails with a toast if there is no room) |
| `Ctrl` + `LMB` | **quick-move** to the paired container: inventory ↔ stash, inventory → vendor sell, vendor → inventory (buy), ground → inventory. Uses `findPlacement`; refuses with `ui.error` if there is no room |
| `Shift` + `LMB` on a stack | open the **split chip**: a 120 × 44 e3 popup at the cursor with a 1..n−1 slider and a mono readout; `Enter` confirms, `Esc` cancels |
| `Shift` + `RMB` on a consumable in the inventory | use it in place, without moving it to the belt |
| `Alt` held | reveal roll ranges in tooltips (§5.3) |
| double-`LMB` on a consumable | use it |

Every one of these is refused, not partially applied, when the destination cannot
accept the item. There is no state in which an item exists in two places or in
none.

### 6.5 Sorting

`⟳ SORT` in the inventory and stash headers calls `items.sortContainer(c)` (§16).
The order `items` must implement, so the result is predictable:

1. Equipment by `SLOT_ORDER`, then jewelry, then consumables, then quest items,
   then everything else.
2. Within a class: descending `RARITY_ORDER` ordinal, then descending
   `reqLevel`, then ascending `baseId`.
3. Placement: largest footprint first (`invW·invH` descending), first fit,
   row-major.

Sorting is **undoable for 5 s**: the toast `toast.sorted` carries an `UNDO`
chip that restores the pre-sort layout from a snapshot of `cells` and the items'
`grid` coordinates, taken before the call.

### 6.6 Container matrix

Legal moves, and what each one calls. A blank cell is forbidden.

| From ↓ / To → | inventory | stash | belt | equipment | vendor | ground |
|---|---|---|---|---|---|---|
| **inventory** | `place` | `place` (town only) | `place` (consumable) | `equip` | `vendorSell` | `dropToGround` |
| **stash** | `place` | `place` | `place` (consumable) | `equip` | | |
| **belt** | `place` | `place` (town only) | `place` | | `vendorSell` | |
| **equipment** | `unequip` | | | `equip` (slot swap) | `vendorSell` | |
| **vendor** | `vendorBuy` | | `vendorBuy` (consumable) | | | |
| **ground** | `pickUp` | | | | | |

The stash and the vendor exist only in Last Bastion; `world.isTown` gates every
move that touches them, and the panels cannot be opened outside town at all.

## 7. Procedural item icons

**Ownership note.** `02-api-contracts.md` §11 makes `items` the owner of item
icons (`items.icon(item) => OffscreenCanvas`) and forbids every other subsystem
from drawing one, because the rarity frame and tint are part of the readability
contract. This section therefore specifies the **contract `ui` consumes and the
recipes `items` must implement**, together with the primitive library. `ui` owns
only the *skill*, *status* and *glyph* icons of §7.6, which have no owner in the
API tables.

### 7.1 Resolution and cache

| Property | Value |
|---|---|
| authored resolution | **64 px per grid cell** — a 1 × 1 icon is 64 × 64, a 2 × 3 is 128 × 192 |
| displayed size | `40·w × 40·h` CSS px at k = 1 (cell 44 minus a 2 px inset each side) |
| supersampling at k = 1 | 1.60 × — crisp at DPR 1, native at k = 1.6 |
| surface | `OffscreenCanvas` with a `2d` context; `imageSmoothingQuality = 'high'` on blit |
| cache key | `` `${baseId}\|${rarity}\|${socketCount}\|${superior ? 1 : 0}` `` |
| cache | LRU, **192** entries; eviction disposes the canvas |
| generation cost budget | ≤ **1.2 ms** per icon, ≤ 6 icons generated per frame; a queue drains during `lateUpdate` and a not-yet-drawn cell shows a `--ash-700` placeholder with the rarity frame already applied |
| determinism | every random value comes from a `Rng` seeded with `ItemBase.iconSeed`, forked per icon, never from `ctx.rng` directly |

Icons are generated lazily on first display, plus eagerly for the whole vendor
stock during the vendor panel's open animation (behind the 130 ms fade), and for
every equipped item during `prewarmMaterials`.

### 7.2 The drawing primitives

All primitives take `(g, rng, p)` where `g` is the 2D context in **icon space**
(origin top-left, `64·w × 64·h`), and all lengths are in that space. The
library lives in `src/items/icons/primitives.js`.

| Primitive | Signature | Produces |
|---|---|---|
| `taper(x0,y0,x1,y1,w0,w1)` | tapered quad path | blades, hafts, spikes |
| `blade(len,w,curve,edge)` | tapered quad + a 1 px inner fuller line + a 2 px light edge on the +x side | every sword, axe edge, dagger |
| `haft(len,w,wrap)` | vertical bar + `wrap` bands of a darker tone at 3 px pitch | every hafted weapon |
| `pommel(r,shape)` | disc / faceted hexagon / claw | weapon butts |
| `guard(span,thick,sweep)` | horizontal bar, optionally arced | crossguards |
| `plate(w,h,curve,rivets)` | rounded-top rectangle with `rivets` 2 px studs on its edge | armour, shields |
| `scale(w,h,rows,cols)` | overlapping scallops | mail, scale armour |
| `cloth(w,h,folds)` | a polygon with `folds` sine-perturbed edges | robes, rags, cloaks |
| `boot(w,h)` | L-shaped silhouette with a sole band | greaves and boots |
| `ring(r,thick,gem)` | annulus + an optional faceted gem | rings |
| `chain(x0,y0,x1,y1,links)` | `links` interlocking ellipses | amulets |
| `bottle(w,h,neck,fill,liquid)` | glass silhouette, a fill polygon, a 2 px meniscus, a cork | potions |
| `scroll(w,h,rollRadius)` | a parchment rectangle with two rolled ends and 3 ink lines | scrolls |

| `skullMask(w,h)` | a rounded cranium with two eye voids and a jaw line | helms |
| `wear(strength)` | post-pass: erodes 1–3 px notches from the silhouette edge at `strength` frequency | every metal item |
| `grime(strength)` | post-pass: multiply-blends a low-frequency value-noise field into the lower half | every item |
| `rim(colour,width)` | 1 px outer contour of everything drawn so far, extracted by an alpha dilate | every item |

Anything that depends on the *actor* (unusable, new) is a `ui` CSS treatment;
anything that depends on the *item* (rarity, sockets, identify, broken) is baked
into the cached bitmap. That split is what keeps the cache key short.

### 7.6 Skill, status and glyph icons — owned by `ui`

**Current versus next.** `ui` calls `skills.describe(actor, skillId, level, out)`
(§16) twice — once at the effective level and once at `level + 1` — and prints

in both. At allocated level 20 the right column reads `— MAXIMUM —` in `--gilt`.

### 8.4 Allocation, confirm and undo

Points are **provisional inside the panel session**:

| Input | Effect |
|---|---|
| `LMB` on a node | if `skills.canAllocate(actor, id).ok` and pending points remain, `pending[id] += 1` |
| `RMB` on a node | if `pending[id] > 0`, `pending[id] -= 1`; **never** removes an already-confirmed point |
| `Shift` + `LMB` | add points until the next tier threshold, the maximum, or the budget runs out |
| `CONFIRM` | for each pending point, in ascending tier then ascending skill-registry order, call `player.spendSkillPoint(skillId)`; play `ui.skillpoint`; clear `pending` |
| `REVERT` | clear `pending` |
| closing with pending points | a confirm dialog: `Confirm 2 skill points?` / `Discard` / `Cancel` |

`canAllocate` is re-evaluated against `allocated + pending` on every change, so a
prerequisite satisfied by a pending point immediately unlocks its child — which
is what lets a player plan a whole tier before committing.

**This is a deliberate deviation from D2**, where a point is spent the instant it
is clicked and cannot be taken back. The reason is stated in §17. The respec
scroll (`consumable.effect === 'respec'`, raising `ui:respec-request`) remains the
only way to undo a *confirmed* allocation, and the confirm dialog says so.

Points earned while the panel is open (impossible in practice, but the harness can
do it) refresh the budget line on the next frame; `pending` is never allowed to
exceed `hudState.skillPoints`.

## 9. Ground item labels

The genre's signature. DOM nodes at layer 20 with `pointer-events: auto` — they
are the only world-anchored thing a player clicks.

### 9.1 Label anatomy

```
┌─┬──┬──────────────────────────┬──────┐   height 22 px
│▌│◈ │  Keen Battle Axe         │      │   seam 2 px, mark 10 px, text --t-body
└─┴──┴──────────────────────────┴──────┘   padding 0 8, fill rgba(13,11,9,.78)
```

| Part | Spec |
|---|---|
| seam | 2 px, the rarity colour, full height |
| rarity mark | the §12.1 mark, 10 × 10, 4 px after the seam |
| text | `--t-body` 13/18 in the rarity colour, `--sh-o1` outline, max width 260 px, `text-overflow: clip` (never ellipsis — a truncated item name is worse than a wrapped one, so the label wraps to a second 22 px line instead, up to 2 lines) |
| quantity | `× 3` appended in `--ink-2` for stacks |
| plate | `rgba(13,11,9,.78)` with the Ash Dissolve on its right edge only |
| stem | a 1 px vertical `--ink-3` line from the label's bottom-centre to the item's projected world point, drawn **only** when the label was displaced by more than 6 px by decluttering |

Position: `render.worldToScreen(item.ground.x, groundY + 0.35, item.ground.z)`,
then the label is centred horizontally on that point with its bottom edge 6 px
above it.

### 9.2 Show rules

A label is a candidate when **any** of these hold:

1. The item dropped within the last **5.0 s** (a fresh-drop grace window).
2. The pointer is within 30 px of the item's projected point.
3. `Alt` is held (`ui.setLootLabels(true)`).
4. `SettingsSave.alwaysShowLoot` is on.
5. The item's rarity is `unique` — uniques are **always** labelled, at any
   distance inside the zone's active radius. Missing a unique because it fell
   behind a rock is not an acceptable outcome.

Gold and consumables are suppressed unless rule 3 or 4 applies, because they are
the bulk of a pack's drop and they are the least interesting.

Candidates are limited to items within **24 m** of the player and inside the
viewport plus a 60 px margin.

### 9.3 Priority and budget

Budget: **16 labels**, from a preallocated pool of 16 × 3 = 48 DOM nodes.

```
priority = RARITY_ORDER.indexOf(rarity) * 10000
         + (unidentified ? 4000 : 0)
         + (freshDrop    ? 2000 : 0)
         − distanceToPlayerMetres * 40
```

Candidates are sorted by descending priority; the top 16 get labels. If more than
16 remain, a single **overflow chip** is placed at the centroid of the remainder:
`+ 7 items` in `--ink-2` on an e1 plate, with the highest rarity among them as
its seam colour. Holding `Alt` while the chip is visible raises the budget to 16
and re-sorts — it does not raise the node count, so the chip persists whenever
there genuinely are more than 16.

Sorting runs at **10 Hz**, not per frame; positions update every frame.

### 9.4 Decluttering — 15 items in one drop

Labels never overlap. After positioning:

1. Compute each label's rect (width is known — it was measured once at build).
2. Sort by ascending `y`.
3. Four relaxation passes: for each label after the first, if its rect intersects
   any earlier rect, move it **up** by `overlap + 4 px`. Upward, because the
   item is below the label and a stem line pointing down reads correctly.
4. If a label would leave the top of the viewport, it moves **down** past the
   colliding group instead, and its stem is drawn upward.
5. Horizontal jitter is **never** applied — a label whose x moves loses its
   association with its item.

After relaxation, any label displaced by more than 6 px gets a stem.

**The damage-number exclusion.** A label rect is registered with the damage-number
system for the frame; a damage number whose spawn point falls inside a label rect
expanded by 8 px is offset upward by 26 px. This is the mitigation that makes the
lightning-yellow versus rare-yellow adjacency (§2.1.6) a non-issue.

### 9.5 Click-to-pick-up

- **Hit target:** the label's own rect (22 or 44 px tall, ≥ 90 px wide) **plus** a
  28 px-radius invisible disc at the item's projected world point, which is a
  separate 56 × 56 node in the same pool entry.
- `pointerdown` on either calls `player.pickUpOrder(item.uid)` (§16), which walks
  the character into range and picks up. `stopPropagation()` is called so the
  click never also becomes a move order to that spot.
- Because labels never overlap after relaxation, the click target is
  unambiguous. The disc targets *can* overlap; when they do, the one belonging to
  the higher-priority item is on top, because pool entries are appended in
  priority order and later siblings paint over earlier ones.
- Hovering a label shows the full item tooltip (§5) after a 60 ms delay, anchored
  to the pointer.
- A label whose item is picked up or despawns fades over 140 ms and returns to
  the pool.

## 10. Feedback layer

### 10.1 Damage numbers

Drawn to `#cl2-fx`, a full-viewport 2D canvas at layer 25, sized
`vw · dpr × vh · dpr` on resize only, with
`setTransform(dpr, 0, 0, dpr, 0, 0)`. **No DOM node is involved.**

**Pool:** `DamageNumber`, owner `ui`, sizes **64 / 96 / 128 / 128** by quality
preset (`01-data-model.md` §11.1). Overflow recycles the oldest. Additionally, no
more than **24 are drawn per frame**; beyond that the lowest-value numbers are
skipped for that frame (not killed) so the biggest hits always survive a burst.

Record (preallocated, reset per §11.2 of the data model):

```js
{ x:0, y:0, z:0,        // world spawn point
  sx:0, sy:0,           // last projected screen point
  t:0, life:0,
  drift:0, riseScale:0, // per-record jitter from the ui RNG fork
  text:'',              // built ONCE at spawn, never per frame
  colour:'#e8e2d4', size:20, crit:false, kind:'hit',
  targetId:0, sourceId:0, lastMergeT:0 }
```

**Motion** (parametric on `u = t / life`, `dt`-integrated):

```
rise   = easeOutCubic(min(1, u * 1.15)) * 52 * k * riseScale     // px, riseScale ∈ [0.88, 1.16]
drift  = jitter * k * easeOutQuad(u)                              // jitter ∈ [−20, +20] px
pop    = 1 + 0.36 * (1 − easeOutQuint(min(1, u / 0.10)))          // 0 → 100 ms
alpha  = u < 0.60 ? 1 : 1 − easeInQuad((u − 0.60) / 0.40)
screen = worldToScreen(x, y + 1.35, z)                            // 1.35 m above the impact
draw at (screen.x + drift, screen.y − rise) with scale `pop`
```

| Kind | Life | Base size | Colour | Extra |
|---|---|---|---|---|
| `hit` | 0.85 s | 20 px | element colour (§2.1.6) | — |
| `crit` | 1.15 s | 27 px | crit variant | a 2 px ring expanding 0 → 34 px over the first 160 ms at 45 % alpha |
| `heal` | 0.90 s | 20 px | `#7fd88f` | prefixed `+`, rises 1.3 × as far |
| `dot` | 0.70 s | 16 px | element colour at 78 % | no pop, half drift |
| `immune` | 1.00 s | 17 px | `#8c8375` | text `IMMUNE` (`combat.immune`) |
| `miss` | 0.80 s | 17 px | `#8c8375` | text `MISS` |
| `block` | 0.80 s | 18 px | `#b8c4cc` | text `BLOCK` |
| `absorb` | 0.80 s | 17 px | `#c78fff` | text `ABSORB` |

**Rendering** uses the display serif at the record's size, `textAlign:'center'`,
`textBaseline:'alphabetic'`, and an outline produced by
`strokeStyle = '#070605'; lineWidth = 3·k; lineJoin = 'round'; strokeText()` then
`fillText()`. **`shadowBlur` is forbidden** — it is the single most expensive
thing a 2D context can do per glyph, and the outline reads better anyway.

**Coalescing — the rule that makes 25 monsters survivable.** On
`actor:damage`, if a live number exists with the same `targetId`, the same
`kind`, and `t − lastMergeT < 0.12 s`, the incoming amount is **added** to it, its
`text` is rebuilt, `lastMergeT = t`, and its `pop` phase restarts (`t` is pulled
back to `min(t, 0.10 · life)`). No new record is drawn. Otherwise a new record
spawns. Per target, at most **3** live numbers may exist; a fourth forces a merge
into the youngest.

**Damage filter** (`SettingsSave.damageNumberMode`): `off` draws none; `own`
(default) draws only numbers whose `sourceId` is the player or a player-owned
summon; `all` draws everything including monster-on-monster.

`ui.floatingText(x,y,z,text,colour)` uses the same pool and the same motion with
`life = 1.4 s`, `size = 15 px`, no pop — this is what `+120 XP`, `NO MANA` and
`RESISTED` use.

### 10.2 Hit flashes

Actor flashes belong to `actors.flash()` and are not `ui`'s. `ui` contributes two
screen-space flashes:

| Flash | Trigger | Geometry | Curve |
|---|---|---|---|
| damage taken | `actor:damage` where `target` is the player | a full-screen radial `rgba(150,16,10,α)` from 40 % to the edge, `mix-blend-mode: screen` | `t += dt/0.19`; `α = peak·(1 − easeOutQuad(t))·0.8`, `peak = 0.35 + 0.65·min(1, amount/(0.18·maxLife))` |
| resource spent from life | `essence_burn`, `last_stand` | the same layer in `--property` | fixed peak 0.30, 240 ms |

### 10.3 Screen impulse on player damage

`ui` calls `render.screenImpulse(strength, dirX, dirY)` where
`strength = clamp(amount / (0.20 · maxLife), 0, 1)` and `(dirX, dirY)` is the
normalised screen-space direction **from** the damage point **to** the screen
centre, obtained from `render.worldToScreen(result.pointX, pointY, pointZ)`.
`ui` additionally calls `player.cameraShake(0.35 · strength)`.

Rate limit: at most one impulse per 120 ms; within that window strengths are
`max`-combined and applied at the end of the window, so a Carrion Swarm's six
simultaneous bites produce one punch, not six.

### 10.4 Low-life vignette

A single DOM node at layer 10, `pointer-events: none`.

```
f = clamp01((0.35 − lifeFraction) / 0.35)          // 0 above 35 % life
shown = damp(shown, f ** 1.25, 7, dt)
```

| Band | Effect |
|---|---|
| `shown` > 0.004 | vignette layer visible; `radial-gradient(ellipse 78% 74% at 50% 50%, transparent 60%, rgba(150,14,10,.34) 88%, rgba(90,8,6,.62) 100%)` at `opacity = shown` |
| life < 0.20 | a heartbeat: `hz = lerp(1.15, 2.35, clamp01((0.20 − life)/0.20))`, `phase += dt·hz`, `thump = e^(−(p/0.085)²) + 0.55·e^(−((p−0.235)/0.10)²)`; the vignette scales `1 + 0.022·thump` and the life orb's numeral scales `1 + 0.05·thump` |
| life < 0.12 | desaturation layer mounts: `backdrop-filter: saturate(.62) contrast(1.04)` at `opacity = shown·0.8` |

The `backdrop-filter` node is `display: none` whenever its opacity is below
0.01 — an unmounted backdrop filter costs nothing, a mounted one at zero opacity
costs a full-screen readback every frame. The heartbeat's integer beat index
change fires `audio.playUi('player.heartbeat', 0.35 + intensity·0.5)`.

The vignette is suppressed entirely while the death screen or the main menu is up.

### 11.1 Ownership

`ARCHITECTURE.md` and `02-api-contracts.md` §13 are explicit: **`player` is the

### 11.4 UI versus world hit-testing

This is the rule the brief calls out twice, and it has exactly five parts.

1. **The overlay is transparent by default.** `.cl2-ui` and every layer element
   carry `pointer-events: none`. Only these opt in with `pointer-events: auto`:
   panels and everything inside them, the plinth plate, ground-item labels and
   their discs, modal scrims, and buttons. Tooltips and the drag ghost are
   `none` and always will be.

2. **`ui.pointerOverUi` is the contract.** `ui` installs one
   `pointerdown`/`pointermove` listener on `document` in the **capture** phase
   whose only job is:
   ```
   pointerOverUi = eventTarget is a Node && uiRoot.contains(eventTarget)
                                          && eventTarget.closest('[data-ui-solid]') !== null
   ```
   No `elementFromPoint`, no `getBoundingClientRect` — `event.target` is already
   the hit result, and `closest()` walks at most 6 ancestors. `pointerOverUi` is
   a plain boolean property, `Fixed = Y`, and `player` reads it in
   `fixedUpdate` before converting a latched click into a world order.

3. **Interactive nodes stop propagation.** Every `pointerdown` handler on a
   `[data-ui-solid]` node calls `stopPropagation()`, so the canvas's own listener
   never sees it. A UI click can never *also* be a world click.

4. **The close-click guard.** When a `pointerdown` closes a panel, `ui` sets
   `pointerOverUi = true` and holds it for one additional frame
   (`_swallowUntilFrame = render.frameIndex + 2`). This kills the classic bug
   where dismissing a panel walks the character into a pack.

5. **The plinth swallows.** The bottom 140 px plate is `[data-ui-solid]` in its
   entirety, including the orbs and the ledgers. This costs 13 % of the screen as
   a click dead zone, and it is the right trade: the alternative — a plate that
   is decorative in some places and interactive in others — produces a player who
   cannot predict whether a click will move them. The camera keeps the character
   above the plinth at all times (`08-characters-visual.md`'s camera geometry puts
   the focal point at screen centre), so the dead zone is never where the player
   needs to click. The XP bar's hover readout is detected inside the plinth's own
   handler, not by a separate solid node.

**Cursor.** `ui` sets `document.body.style.cursor` from a fixed table, written
only on change: `default` over the world, `pointer` over an interactive UI node,
`grabbing` while dragging an item, `crosshair` while a ground-targeted skill is
armed, `not-allowed` over an invalid drop target. All are CSS keywords — no
cursor image, because there are no assets.

### 11.5 Rebinding

The Controls tab of the options screen lists every rebindable action with its
current `KeyboardEvent.code`. Clicking a row arms it; the next `keydown` (routed
through `player`, which forwards it via `ui.captureBinding(code)`) assigns it.

- **Conflicts steal.** Assigning a code already in use unbinds the previous owner
  and highlights that row in `--danger-ink` with `controls.unbound`.
- Reserved codes are rejected with `ui.error` and `controls.reserved`.
- `RESET TO DEFAULTS` restores the table above.
- Bindings live in `SettingsSave.keybinds` (§16) as `{ actionId: code }` and are
  written through `save.saveSettings()`. Codes are physical
  (`KeyQ`, `Digit1`), so a Cyrillic or AZERTY layout keeps the same physical
  keys.
- The displayed key name is `key.<code>` in the i18n dictionary, with a fallback
  that strips the `Key`/`Digit` prefix.

## 12. Accessibility and readability

### 12.1 Rarity under colour blindness — the explicit solution

The rarity hexes are fixed by the data model and **cannot be changed**; they are
"sacred". So the answer cannot be recolouring. It is **four redundant channels**,
each of which alone is sufficient to identify a rarity.

**Channel 1 — luminance.** The four distinct rarity luminances are
`magic 0.245 < unique 0.348 < normal/superior 0.578 < rare 0.755`. Under total
achromatopsia these render as four clearly separated greys; the smallest adjacent
gap is 0.103, which at these levels is roughly 1.4 : 1 of relative contrast
between neighbours — visible. Every rarity also clears **4.5 : 1** against the
panel fill (§2.1.4), so no rarity is ever merely *legible-if-you-squint*.

**Channel 2 — shape: the rarity mark.** Every surface that carries a rarity
colour also carries a mark whose *silhouette* is unique. The marks are drawn with
CSS box geometry, never as a font glyph, so they cannot be lost to a missing
character. Base size 10 × 10 px at k = 1 (13 × 13 in colour-blind mode).

```
normal      (nothing)

superior    ▄▄▄▄▄▄▄▄        one bar        8 × 3
            
magic       ▄▄▄▄▄▄▄▄        two bars       8 × 3, 3 px apart
            ▄▄▄▄▄▄▄▄

rare           ◇            open diamond   10 × 10, 2 px stroke

unique         ◈            filled double  12 × 12 outer, 6 × 6 inner
```

The mark appears on: the icon (baked, §7.4), the ground-item label, the tooltip
name line (12 px, 6 px before the text), the loot toast, the minimap marker (as a
stroke width: 0 / 1 / 1-dashed / 2 / 2-double), and the vendor list row.

**Channel 3 — words.** `SettingsSave.rarityLabels` defaults to **on**. Every
tooltip prints the rarity word (`Superior`, `Magic`, `Rare`, `Unique`) under the
base type; a `normal` item prints nothing, which is itself unambiguous. This is
the cheapest possible fix and it is on by default because the cost of the extra
line is a line.

**Channel 4 — position and grouping.** Vendor and stash lists group by rarity in
`RARITY_ORDER`, so position carries information even when colour does not.

**Colour-blind mode** (`off` / `protan` / `deutan` / `tritan`) does **not**
recolour rarity — it cannot. It:

- raises the mark size from 10 to 13 px and its stroke from 2 to 3 px,
- forces `rarityLabels` on and disables the toggle,
- raises every rarity frame stroke from 1 px to 2 px,
- swaps the *chrome* accent set (which is not sacred) for a per-deficiency
  alternative: `protan` and `deutan` move `--verdigris` → `#3f86c8` (blue) and
  `--good-ink` → `#69a8d0`, so gain/loss deltas separate on the blue–yellow axis
  instead of red–green; `tritan` moves `--gilt` → `#d06fb0` and `--property` →
  `#5fc8d0`.

**Bloom and tonemapping.** In the UI this is solved structurally: the DOM overlay
is composited by the browser **after** the WebGL canvas, so nothing in the HUD
passes through AgX, bloom or the grade LUT. A `#ffe066` rare label is
`#ffe066` on the wire. The at-risk surface is the world-space loot glow, which
`fx` owns; the requirement `ui` places on it, and which `ARCHITECTURE.md`'s
quality bar already implies, is: **`fx.lootGlow` must draw in an overlay pass
after tonemapping, sampling `materials.rarityColour()` unmodified.** The DOM
label is always drawn on top of the glow, so even if the glow drifts the readable
channel does not.

**The ember exclusion rule** (§2.1.3) closes the last hole: the chrome accent
`#e0622a` is never applied to a surface that also carries a rarity colour, so a
protanope never has to separate ember orange from unique gold.

### 12.2 Contrast

Minimum ratios, measured against `--ash-800` `#16130f` and asserted by a
boot-time dev check that walks the token table:

| Content | Minimum | Actual worst case |
|---|---|---|
| body text, labels, values | **4.5 : 1** | `--ink-3` at 5.03 : 1 |
| text ≥ 15 px semibold, and all display text | **3.0 : 1** | `--verdigris` at 4.85 : 1 |
| rarity text | **4.5 : 1** | `magic` at 5.27 : 1 |
| 1 px borders and rules | **1.6 : 1** | `--ash-500` at 1.9 : 1 |
| disabled text (`--ink-4`) | exempt | 2.48 : 1 — **never information-bearing** |

Text over the *world* (ground labels, damage numbers, world prompts) does not
have a fixed background, so it is not measured by ratio; it is guaranteed by the
mandatory `--sh-o1` outline (DOM) or `strokeText` at 3 px (canvas), which puts a
`#070605` ring around every glyph. That ring gives ≥ 12 : 1 against the glyph
itself regardless of what is behind it.

### 12.3 Text size floor and scaling

- **No text below 11 px, ever**, at any resolution, at any `uiScale`. `--t-micro`
  is 11 px and `k ≥ 1.0` guarantees it.
- `uiScale` offers 85 / 100 / 115 / 130 %; the 85 % option is disabled below
  1080p because it would break the floor (11 × 0.85 = 9.35 px).
- Line-height is never below 1.18 × the font size.
- No text is justified, no text is letter-spaced below 0 em, and body text is
  never uppercase — uppercase is reserved for labels of 3 words or fewer.

### 12.4 The dense-fight rule

> **You must be able to read the fight with 25 monsters and 8 spell effects on
> screen.** Concretely: with the `dense` capture staged, a player must be able to
> state their own life fraction, the target's life fraction, and the rarity of the
> nearest drop within **2 seconds** of the frame appearing.

Six mitigations enforce it, and each is verifiable:

1. **The combat window is chrome-free.** The rectangle x 264…1656, y 96…892 at
   1080p carries no chrome at all — only world-anchored labels and damage
   numbers. Every persistent readout lives outside it. Verified by a dev assert
   that walks the chrome layer's computed geometry table.
2. **Damage numbers are capped and coalesced** (§10.1): ≤ 24 drawn per frame,
   ≤ 3 per target, 120 ms merge window, and `damageNumberMode: 'own'` by default
   so monster-on-monster damage is silent.
3. **Ground labels are capped and decluttered** (§9.3–9.4): ≤ 16, never
   overlapping, overflow collapsed into one chip.
4. **The label/number exclusion band** (§9.4): a damage number never lands inside
   a ground label's rect + 8 px.
5. **Every world-anchored glyph carries a hard outline** (§12.2), so readability
   does not depend on what `fx` drew underneath.
6. **The hue budget.** The interface reserves `--ember` (chrome), `--gilt`
   (gold/XP) and the five rarity hues. `fx` reserves the six element hues for
   damage and the red/orange band for enemy telegraphs and the cyan band for
   player ground effects (`ARCHITECTURE.md` § Quality bar). Neither side uses the
   other's band inside the combat window.

**Acceptance:** a `dense` shot in the baseline set — 25 monsters, one champion
with a health bar, 8 concurrent `fx` effects, 20 live damage numbers, 12 ground
items with 6 labelled, the player at 28 % life so the vignette is up. It goes
through `tools/imagediff.mjs` like every other shot, and it is the shot the
adversarial critic is pointed at during M8.

### 12.5 Other accessibility affordances

| Concern | Provision |
|---|---|
| motion sensitivity | `SettingsSave.reduceShake` scales `render.screenImpulse` and `player.cameraShake` by 0.25 and disables the low-life vignette's heartbeat scaling (the vignette itself stays — it is information) |
| photosensitivity | no element flashes faster than 3 Hz; the fastest is the sub-2 s buff pulse at 0.95 Hz and the rage bezel at 0.54 Hz |
| audio-only cues | none. Every audio cue in `10-audio.md`'s UI section has a visual counterpart in this document |
| pointer precision | every clickable target is ≥ 28 × 28 px except grid cells (44 × 44) and the close glyph (24 × 24, which has a 36 × 36 hit rect) |
| readability of numbers | every numeral is tabular-figured monospace so a changing counter never reflows |
| language | full RU dictionary (§14); the layout is authored with a **1.35 × string-length headroom** on every label, which is the measured EN→RU expansion for short UI strings |

### 13.3 No allocation per frame

| Source of garbage | Rule |
|---|---|
| `new` anything | forbidden in `lateUpdate`. Every record, array, `Vec3`-shaped scratch and pool entry is built in `init()` |
| `player.hudState()` | called with a preallocated `HudState` out-parameter |
| `render.worldToScreen()` | called with a preallocated out-parameter |
| `items.groundItemsNear()` | called with a preallocated array whose `length` is reset in place, never reassigned |
| number → string | a **preallocated LUT of the strings `"0"`…`"9999"`**, built once in `init()` (≈ 90 KB), covers every counter, stack count, cooldown second, gold digit group and damage number below 10 000. Values above use `formatBig()`, which is called at most once per *spawn*, never per frame |
| `toFixed()` | forbidden in `lateUpdate` except inside `setStyle`'s change-guard, and even there the value is pre-quantised so the guard usually short-circuits |
| template strings for `transform` | quantised first: positions to 0.5 px, scales to 1/1000, opacity to 1/1000, angles to 1°. A quantised value that did not change writes nothing |
| closures | no arrow function is created in `lateUpdate`. Event handlers are bound once in `init()` |
| `Map`/`Set` iteration | forbidden per frame where it boxes an entry; the buff strip iterates a dense array |
| `classList.toggle` | routed through the cached `setClass` helper so an unchanged class writes nothing |

**Budget:** ≤ **64 short strings** allocated per frame in the worst case (a full
hotbar on cooldown plus 24 buff timers plus 16 moving ground labels). That is
roughly 2 KB/frame, ≈ 120 KB/s, which the nursery absorbs without a visible
collection. `tools/profile.mjs` attributes any regression to `ui` directly.

### 13.4 Reflow avoidance

1. **No layout read in `lateUpdate`.** `getBoundingClientRect`, `offsetWidth`,
   `offsetHeight`, `scrollHeight`, `getComputedStyle` and `elementFromPoint` are
   forbidden there, and a dev build monkey-patches them to throw while
   `inLateUpdate` is true. This is worth the ugliness: one accidental read
   forces a full-document layout every frame.
2. **Measurement is a user-action operation.** The tooltip measures its text once
   on build, writing all its content first and reading `offsetWidth` exactly once
   afterwards. The dialogue panel does the same. Neither happens more than twice
   per user action.
3. **Only `transform` and `opacity` animate.** No per-frame write of `left`,
   `top`, `width`, `height`, `margin` or `font-size`. The two exceptions —
   the cooldown `conic-gradient` angle and the XP fill's `transform: scaleX` —
   are paint-only and composite-only respectively.
4. **`contain: layout style paint`** on `.cl2-ui`, on every panel, on the plinth
   and on every pooled world-anchored entry, so an invalidation cannot escape its
   subtree.
5. **`will-change: transform`** only on nodes that actually move every frame: the
   drag ghost, ground labels, the target-bar fills, the XP chase. Not on
   everything — a promoted layer is rasterised once at whatever sub-pixel
   translation the compositor first saw, which is exactly the bug the reference
   project documented on its compass strip and which made its capture harness
   boot-time-dependent. Do not "optimise" `will-change` back onto static chrome.
6. **Canvas resizing** happens only in `resize()`. Writing `canvas.width` clears
   and reallocates the backing store; doing it per frame is a hitch.
7. **Panel show/hide** uses `display: none` below 0.004 opacity, so a closed panel
   costs nothing — not layout, not paint, not compositing.

## 14. Internationalisation

### 14.1 The mechanism

```js
/** src/ui/i18n.js — two plain objects, no library, no bundler magic. */
export const EN = { 'hud.life': 'Life', /* … */ };
export const RU = { 'hud.life': 'Жизнь', /* … */ };
```

- **Keys are English identifiers**, never English phrases. `hud.life`, not
  `"Life"`. A key is dotted `lowerCamelCase` segments; the first segment is the
  namespace.
- `ui.t(key, params)` looks the key up in the active dictionary, falls back to
  `EN`, and falls back again to the key itself with a `[missing]` prefix in dev
  builds. **It never throws.**
- Parameters are `{name}` placeholders substituted by a single pass over the
  string. The substitution writes into a preallocated buffer for the ≤ 8 keys
  that are called per frame; every other call is a user action and may allocate.
- Numbers inside parameters are formatted by `ui` before substitution — the
  dictionary never contains a format specifier, because a translator cannot be
  expected to maintain one.
- **Plurals** use an explicit suffix convention: a key ending `.one` / `.few` /
  `.many` / `.other`, selected by `pluralRule(lang, n)`. Russian needs all four
  forms; English uses `.one` and `.other`. Only 11 keys need this and they are
  marked in the tables.
- A boot-time dev check asserts that `Object.keys(RU)` is a superset of
  `Object.keys(EN)` minus a declared allowlist, and prints the missing keys.

## 17. Deviations from the plan

**D-11 — Belt potions are on `Q W E R`, not `1`–`4`.**
`IMPLEMENTATION_PLAN.md` §0 locks "1–4 hotbar, potions on keys". Those two cannot
both be `1`–`4`. The hotbar keeps the locked binding and the belt takes the
adjacent home-row block, which is free because click-to-move means `WASD` is
unused. Both are rebindable.

**D-12 — `I` opens the character sheet and the inventory as a pair.**
D2 draws equipment and the grid in one window. Splitting them into two panels
lets each one be sized for its content and lets the stash and the vendor pair
with the grid without a third layout. Opening them together preserves the muscle
memory; `C` opens the sheet alone.

**D-13 — Skill points are provisional until confirmed.**
D2 spends a point the instant it is clicked, irreversibly. That design exists
because D2 had no undo affordance, not because misclicking is good. Points are
provisional within a panel session, with explicit Confirm and Revert; once
confirmed they are as permanent as D2's, and the respec scroll remains the only
way back. The confirm dialog says so, so nobody is surprised.

**D-14 — Damage numbers are canvas, not DOM.**
The plan's §6 says "floating damage numbers (pooled, no allocations)". A pool of
128 DOM nodes rewriting `transform` every frame during a 25-monster fight is 128
string allocations and 128 style invalidations per frame; a canvas is one draw
call region and zero nodes. The pooling requirement is honoured — the pool is of
records, not elements.

**D-15 — The skill-tree connectors are canvas, not SVG.**
`IMPLEMENTATION_PLAN.md` §6 says "DOM + SVG connector lines". Thirty SVG paths
cost thirty nodes and cannot be selectively redrawn for the hover-focus effect
without touching all of them. One canvas with a dirty flag is fewer nodes and
strictly less work.

**D-16 — The corner minimap is always on; `Tab` is the overlay.**
The plan describes the minimap as "overlay like D2 (Tab)". A permanent 240 px
corner map plus a `Tab` overlay is strictly more information for 6 DOM nodes, and
the corner map is what makes the ground-item and champion markers useful during a
fight rather than only between them.

**D-17 — `ui` installs no keyboard listener.**
`02-api-contracts.md` §13 forbids reading `ctx.input` outside `player`. Rather
than carve an exception for the interface, `player` owns every key and calls
`ui`'s toggle methods — which is why §16.1 asks for the three missing toggles and
`captureBinding`. The cost is four extra API rows; the benefit is that there is
exactly one place in the codebase where a key becomes an action.

**D-18 — The plinth swallows clicks along its whole width.**
An alternative design makes only the functional controls solid, so a click on the
decorative plate still moves the character. That produces a player who cannot
predict whether a click will move them, which is worse than losing 13 % of the
screen to a dead zone the camera never needs.
